# skill-engine: Versioning and release doctrine

This reference covers how the engine versions and releases itself, the CI doctrine that keeps its version and its template/example copies in sync, and how an already-stamped contextualizer evolves across plugin major revisions. For the reference and navigator shapes these bumps govern see artifact-contract; for the engine runs and the release ritual that apply them see workflows.

## One ecosystem, one version

The engine plugin, the scaffolder shipped inside it, the `engine-bootstrap-templates/`, and the engine workflows all share a single semantic version — install `skill-engine vX.Y.Z` and every layer is at `X.Y.Z` ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L11-L18)). The three layers are load-bearing together — templates were scaffolded by a given version's scaffolder and may not work with another's engine — so splitting the version into three would mask that coupling; one number is simpler to reason about and test ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L20-L24)).

## Where the current version lives

The canonical version surface is the plugin manifest's `"version"` — the engine carries its version in one place ([`plugin/skill-engine/.claude-plugin/plugin.json`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/.claude-plugin/plugin.json#L3-L5)). The marketplace entry mirrors it at `plugins[0].version`, and both currently read `0.5.0` ([`.claude-plugin/marketplace.json`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/.claude-plugin/marketplace.json#L6-L12)). The release doctrine treats `plugin.json` as the always-bumped surface; the CLI header/variable surfaces belong to the optional per-contextualizer CLI pattern, not to anything the engine itself generates ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L7-L7)).

## Semver posture for a contextualizer

Standard MAJOR.MINOR.PATCH, read through what a contextualizer change means: MAJOR is a breaking change to the install layout, the metadata schema, or the navigator structure (and it triggers a legacy-upgrade flow on existing installs); MINOR adds a reference file to the catalog or a new workflow; PATCH is reference-content, bug, or doc fixes that change what users see after running an update ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L13-L17)).

Internal-only changes — engine refactors, tooling tweaks, doc-only edits to the contextualizer itself rather than the references it ships — do not earn their own patch bump; they collect under a top-of-file `[Unreleased]` section and roll into whatever release next has a real reason to ship ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L116-L131)).

## Release is manual, with two destructive gates

Release is an eight-step manual checklist, and two of its steps are destructive: the commit-and-push and the `gh release create`. Both are manual approval pauses — where a human catches a wrong version or a bad CHANGELOG line — and the doctrine is explicit that they must not be chained into a single automated `/ship` button ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L52-L57)).

This is a deliberate stance: there is no CI-for-releases, because a build server deciding when to ship invites "ship it because it is green" thinking that is wrong for a content-as-source-of-truth project. The narrower CI-for-validation — a `pre-commit` wrapper that just runs the same `verify.sh` the maintainer would run by hand — is supported and opt-in; it augments the reviewer without moving the release decision off them ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L149-L155)). The release ritual itself is encoded as a workflows slash command so the checklist runs the same way every time.

## The template/example byte-sync doctrine (CI-enforced)

Every `examples/<slug>/verify.sh` must be a verbatim copy of `engine-bootstrap-templates/verify.sh`; `doctrine.sh` Check 7 walks the example copies and runs `cmp -s` on each against the template, failing the build on any divergence so a template edit that misses the copies cannot silently leave four drifting ~1,100-line scripts ([`plugin/skill-engine/tests/doctrine.sh`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/tests/doctrine.sh#L330-L347)).

Version parity is mechanically gated the same way. `doctrine.sh` Check 8 reads `plugin.json`, `marketplace.json`, and the README (version badge + prose) and fails CI if they disagree, and a continuation pins the two hand-edited surfaces the four-way check cannot see — SECURITY.md's supported-versions line and the CHANGELOG's top release heading — to `plugin.json`'s version ([`plugin/skill-engine/tests/doctrine.sh`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/tests/doctrine.sh#L349-L394)). The remaining doc example blocks stay manual-review at bump time per the CHANGELOG ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L265-L281)).

## How a stamped contextualizer evolves across majors

Forward compatibility is the default: every template and schema evolves by addition, never deletion or structural change. A newer engine reading an older config supplies a safe default for a missing field, and an older engine reading a newer config ignores the field it does not know — so a MINOR bump requires no migration and an existing contextualizer keeps working unchanged ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L40-L42), [`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L67-L71)).

A genuinely breaking change — restructuring `research/.research-state.json` so old state cannot read it — forces a MAJOR bump with an explicit one-time CLI migration: detect the legacy version from the metadata file, signal the user, migrate (backing up the old state, pausing if the mapping is lossy), validate the migrated state, and record the new version ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L100-L106)).

So a version bump asks little of an already-stamped contextualizer. On a MINOR it does nothing (Option A), or opts into new templates via `scaffold --preserve-existing-references`, which updates the config and templates while preserving existing references and state (Option B), or re-scaffolds fresh (Option C) ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L239-L251)). The backward-compatibility window is narrow by policy — the engine reads only the current and immediately previous MAJOR, and a contextualizer further back upgrades through the intermediate version rather than in one jump ([`plugin/skill-engine/docs/10-version-evolution.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/10-version-evolution.md#L212-L219)).

## What the CHANGELOG records

The CHANGELOG uses a fixed type vocabulary — `add`, `change`, `fix`, `remove`, `deprecate` — one bullet per change, one sentence, the affected path or area in parentheses, focused on the what and why rather than the how, since code lives in git ([`plugin/skill-engine/docs/06-release-doctrine.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/06-release-doctrine.md#L92-L114)). The current head is `[0.5.0] - 2026-06-11`, whose entries record contextualizer selection for the locator skills, an `error` eval-run outcome, the `apply` live-tree gate, and the unification of the cache layout — the kind of user-visible, release-only change the log is meant to capture, with its top heading gated to equal `plugin.json`'s version ([`CHANGELOG.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/CHANGELOG.md#L1-L16)).
