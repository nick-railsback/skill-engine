# nick-railsback/skill-engine — Evaluation, coverage, and self-audit

This reference covers the three measurement-and-drift surfaces that sit above `verify.sh`: SELF-AUDIT (read-only drift detection), the routing eval harness (chapter 12), and the two grounding instruments (chapter 13). They answer different questions — is the corpus drifting, does the description route, are the references verifiable — and none of them is the structural gate.

## SELF-AUDIT: read-only drift detection

SELF-AUDIT runs eight drift checks against a contextualizer's current state: (1) stale `as of` date, (2) broken URL, (3) long-untouched reference, (4) catalog-vs-content disagreement, (5) cross-reference-vs-content disagreement, (6) review-state staleness, (7) paragraph→permalink density, and (8) grounded-citation rate. It is read-only by default — it surfaces a findings table and exits. Source: [`self-audit/SKILL.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/skills/self-audit/SKILL.md#L8-L15).

Its scope is framing drift, not invariant compliance: artifact-contract questions (frontmatter rules, file naming, the four reference invariants) are owned by `verify.sh` and are deliberately not surfaced as SELF-AUDIT findings even when something looks off. Two HARD-GATEs never override — no write without explicit human approval, and pre-approval `verify.sh` validation on the sandbox copy — and every run records one entry per check with no silent skips, each `N/A` carrying its one-line reason. Source: [`self-audit/SKILL.md` § Invariants](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/skills/self-audit/SKILL.md#L96-L119).

Check 4 is the catalog↔reference *framing* check, and it is worth distinguishing from the structural bijection: it diffs each catalog row's one-line description against the reference's body framing (the first paragraph under the H1, or the bullets under a `## When to Use This Reference` section), whereas the structural catalog-bijection 1:1 correspondence belongs to `verify.sh`. Source: [`02-artifact-contract.md` § Check 4 heuristic](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/02-artifact-contract.md#L400-L401).

The audit proposes nothing on its default path; after the findings table it offers an opt-in `y` / `n` / `select` fix flow for only the three deterministic auto-fixable checks — 1 (refresh stale date), 4 (sync catalog row to body framing), and 6 (flip `review_state` to `stale`). The other five (2, 3, 5, 7, 8) are judgment-required: each prints a one-line recommendation and no mutation is drafted. Any accepted fix still passes through the REFRESH propose → sandbox-`verify.sh` → APPROVE gate before touching the working tree. Source: [`self-audit/SKILL.md` § Optional fix flow](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/skills/self-audit/SKILL.md#L397-L437).

## Routing evaluation (chapter 12)

The routing eval harness answers a single question: given a representative consumer query, did the navigator route it to the reference the maintainer expected? A pass means the description's WHEN-condition matched; the test surface is the description's discrimination power — the two failure modes it stress-tests are *too vague* (skill never fires) and *too broad* (skill fires on irrelevant queries) — not the catalog's bijection count or any `verify.sh` invariant. Source: [`12-evaluation.md` § What evals stress-test](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/12-evaluation.md#L22-L26).

Each contextualizer co-locates its own `evals/evals.json` beside `SKILL.md`; every entry carries a `query`, an `expected` routing target (reference filename without `.md`), and free-form `notes`, plus optional `tags` and a `persona`. The framework is bash + jq + JSON plus a single-file HTML viewer and the agent CLI already running the navigator — no third-party dependency, and the engine does not gate on eval presence. Source: [`12-evaluation.md` § Schema shape](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/12-evaluation.md#L27-L44).

Every entry runs three times per invocation, each run recorded `pass`, `fail`, or `error` (an `error` is a CLI-invocation failure — expired auth, broken CLI — carrying no routing verdict, so it is excluded from the pass/fail vote and the denominator; a run where every entry errored exits 70). Three runs exist because language-model routing is non-deterministic at the matching layer, and an entry that flips across the three is flagged as *flickering* rather than averaged into a silent middle. Source: [`12-evaluation.md` § Three runs per query](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/12-evaluation.md#L139-L145).

The eval set is split 70/30 once into physically separate `evals-train.json` and `evals-test.json` files (physical segregation makes over-fitting take work) — the train set is iterated against, the test set run rarely to check generalization — and every entry carries one of three persona values (`domain-expert`, `domain-naive-technical`, `non-technical`) so the renderer can stratify pass rates by audience. Source: [`12-evaluation.md` § The 70/30 split](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/12-evaluation.md#L124-L137).

When comparing two invocations the renderer reports per-query deltas — regressions, gains, flicker stabilizations, and new flicker — and it is deterministic: the same `results-*.json` produces identical output bytes, which is what makes the diff between two runs a meaningful artifact to paste into a pull request. Aggregation is the contract surface; the maintainer reads deltas rather than individual run records. Source: [`12-evaluation.md` § Aggregation contract](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/12-evaluation.md#L147-L160).

## Grounding coverage (chapter 13)

Grounding is a different question from routing: once a reference is in play, is its prose anchored to upstream, and does the model emit that anchor when it answers? Two instruments answer it — Check 7 (`permalink_density.py`, corpus side) and Check 8 (`grounded_rate.py`, answering side) — both wired into SELF-AUDIT and both defaulting to a ≥80% threshold. Source: [`13-coverage-testing.md`](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/13-coverage-testing.md#L1-L13).

Check 7 is a free, bash-local Python lint that walks `references/**/*.md` and marks a prose paragraph *covered* when a SHA-pinned or stable-tag-pinned GitHub permalink appears within five lines; the pass gate is ≥80% corpus-wide. Coverage means verifiability, not correctness — a permalink to the wrong line still counts as covered, so the metric makes claims *checkable*, not *true*. The lint is GitHub-source-blind by design (a check that read a self-authored config field to decide how to grade you would be gradeable on your own answer key), so pure web-doc corpora cannot be credited directly. Source: [`13-coverage-testing.md` § Check 7](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/13-coverage-testing.md#L26-L48).

Check 8 measures *grounded-citation rate* on the answering side: for each `needs_reference` prompt in `research/eval-prompts.json`, the runner invokes the contextualizer's `SKILL.md` as system prompt against Claude Haiku 4.5 with a single `read_reference` tool and grades whether the model both (a) opened ≥1 reference AND (b) emitted a SHA-pinned or tag-pinned GitHub permalink in its final response text — "grounded" requires both, and the permalink regex is imported from the Check 7 lint so the two share one source of truth. Source: [`13-coverage-testing.md` § The grader](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/13-coverage-testing.md#L50-L54).

Check 8 is opt-in — it makes paid Anthropic API calls and only runs when the maintainer sets `SKILL_ENGINE_RUN_EVAL`; absent the opt-in, or with no `eval-prompts.json`, it emits `[N/A]` and calls nothing, while a present-but-malformed corpus is a loud `[FAIL]`. Neither Check 7 nor Check 8 is auto-fixable: the right citation depends on what the paragraph or answer asserts, and the act of citing is the curation work itself. Source: [`self-audit/SKILL.md` § Check 8](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/skills/self-audit/SKILL.md#L286-L299).

The grader is the engine-side claim; the score is downstream. It is verified keyless and deterministically against 18/18 mocked cases (grounded paths inject pre-recorded responses, the rest drive dry-run / schema / N/A paths) with zero API calls; the first live measurement (2026-06-02, MCP example, Haiku 4.5) rose 30% → 90% after the navigator's Claims policy began instructing permalink citation. The engine ships no canonical `eval-prompts.json` — a shared corpus would couple the engine to one contextualizer and invite gaming since the grader sees the prompts. Source: [`13-coverage-testing.md` § The grader, verified](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/13-coverage-testing.md#L52-L62).

## Three trust surfaces: self-audit vs. verify.sh vs. review

The three surfaces are intentionally disjoint. `verify.sh` is the structural gate — a deterministic, blocking, contract-compliance check that must pass before any staged proposal is surfaced. SELF-AUDIT is a read-only drift audit — non-blocking, framing-only, and by default write-free — that surfaces findings the reviewer acts on. Source: [`self-audit/SKILL.md` § Invariants](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/skills/self-audit/SKILL.md#L96-L100).

Review is the human sign-off layer: `/skill-engine:apply` verifies the review *actually ran* (Step 1 predictions filled and Step 2 disagreement set populated in `REVIEW.md`) before promoting a proposal from its `.proposed/` staging directory — a ticked Step-3 box alone is not sufficient. Structural passing (`verify.sh`) and measurement signal (evals, coverage) are inputs to that human decision, never a substitute for it. Source: [`02-artifact-contract.md` § Staging directory shape](https://github.com/nick-railsback/skill-engine/blob/711e3144e1ad81b50414667b9b5e3c0363989955/plugin/skill-engine/docs/02-artifact-contract.md#L45-L45).
